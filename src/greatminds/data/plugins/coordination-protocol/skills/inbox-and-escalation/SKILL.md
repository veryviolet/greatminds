# Inbox and escalation

`greatminds inbox` is the inter-role messaging channel for **out-of-band**
communication that doesn't fit into task-block authoring. Use it for:
asks (need an answer), infos (FYI, no action needed), wake-up nudges
(coordd auto-generates these from journal events).

## greatminds inbox API

```bash
# Send an ask to another role
greatminds inbox send MAINTAINER --kind ask \
  --task <optional task id> \
  --about "<one-line subject>" \
  --body "<markdown body>"

# Send an info (no action expected; acks for record-keeping)
greatminds inbox send ARCHITECT-PLANNER --kind info \
  --about "<subject>" --body "<body>"

# List your inbox (uses $GREATMINDS_ROLE)
greatminds inbox list

# Ack a message after reading + acting (renames wake-… to processed-…)
greatminds inbox ack <filename-or-absolute-path>
```

## Message kinds

- `ask` — sender expects an answer in the form of an inbox reply, a
  task transition, a schema change, or some explicit action.
- `info` — FYI; sender flags something the receiver should know about
  but isn't requesting a response. Still must be ack'd to mark "read".
- `wake-...` — auto-generated by coordd from journal events. Indicates
  "you have new work in queue X" — read your queue, do the work, then
  ack the wake.

## Inbox directory convention

`coordination/inbox/<role-lowercase>/` — that's it. Lowercase role
names ONLY (`technical-writer`, NOT `TECHNICAL-WRITER`). `greatminds inbox`
lowercases inputs automatically; never craft a path with uppercase
directly (legacy uppercase dirs were purged — see git history).

## MAINTAINER vs ARCHITECT-PLANNER — routing of escalations

This is the most common confusion point. When you need to escalate
something outside your own queue, who do you send to?

| If the issue is about… | Route to |
|---|---|
| Agent X is dead / stuck / not responding | **MAINTAINER** |
| Schema rule needs amending | **MAINTAINER** |
| Stand infrastructure is broken | **MAINTAINER** (and SK for the actual stand) |
| Bin/* script defect | **MAINTAINER** |
| Coord-init / coordd / cutover problems | **MAINTAINER** |
| Plan-block ambiguity / contradiction | ARCHITECT-PLANNER |
| New feature request from USER | ARCHITECT-PLANNER (via user_feedback) |
| Bug found by using the product | ARCHITECT-PLANNER (via user_feedback) |
| Architectural / trade-off question | ARCHITECT-PLANNER |
| READER findings → write task | ARCHITECT-PLANNER |

When genuinely uncertain, MAINTAINER and PLANNER can forward to each
other via `greatminds inbox send <other> --kind ask`. Better to over-route
than under-route — silent drops are the worst outcome.

## When to send vs when to write a task block

- Inter-role question about a specific task that doesn't change its
  status → **inbox ask** (e.g., "what did you mean by X in the plan?")
- A finding that should change a task's state → **block** authored
  via `greatminds task append-block` (e.g., TESTER writes `tests` block with
  outcome=fail; READER writes `reader_review` block).
- Out-of-band notification (process / schema / infra) → **inbox info**
  or **ask**.

When in doubt: if your message affects only the human/agent receiving
it (no task state change), it's inbox. If it changes a task's status
or evidence, it's a block.

## Coordd wake-up mechanics

`coordd` is a systemd --user service that watches `journal.ndjson`
and your `inbox/<role>/` directory. When a task lands in your owned
queue, coordd posts a `wake-...` message to your inbox; if your /loop
agent is currently sleeping (waiting for next tick), it gets nudged
awake. Chat-mode roles (PLANNER, MAINTAINER) do NOT receive keystroke
nudges — coordd only writes the inbox file; they read it whenever
they're active.

You don't interact with coordd directly. Just keep your inbox
processed (ack messages after acting on them); coordd does the rest.
